# 검색 품질 회귀셋

의미(벡터) 검색이 "코드는 멀쩡한데 결과가 나빠지는" 부류의 회귀를 잡는다. v3.8.8 의
마스킹 별표 수정이 첫 사례 — 정보공개포털 결재문서의 `*******` 가 임베딩 토큰의 절반을
삼켜 top-1 이 77% 에 머물렀는데, 단위테스트로는 잡을 수 없는 종류였다.

## 구성

- `corpus/<id>.md` — 실제 공공문서 50건의 kordoc 마크다운 (정보공개포털 결재문서
  40 + 정책브리핑 보도자료 10, 원본은 `kordoc/bench/corpus`). 5분류 × 10 (보도자료·
  여비수당지급·결과보고·알림요청회신·계획). 라벨은 `manifest.json`.
- `queries.json` — 검색어 44개와 기대 문서. 제목 복붙이 아니라 사용자가 칠 법한
  패러프레이즈("도서관 실내 공기질 측정 결과" → 실내공기질 측정 결과보고).
- `bench.py` — Rust 인덱싱 파이프라인(표 직렬화·그림 참조 제거 → 600/150 청크 → normalize →
  별표 접기 → KoSimCSE int8, 토큰 128 절단)을 파이썬으로 재현해 문서 점수 = max chunk cosine 으로
  top-1 / top-3 / MRR 을 낸다. **Rust 쪽(`parsers/mod.rs`, `parsers/kordoc/text.rs`)을
  바꾸면 여기도 같이 맞출 것** — 재현이 어긋나면 벤치는 거짓말을 한다.

## 실행

```bash
cd harness/search-quality
python3 -m venv venv && venv/bin/pip install -r requirements.txt
venv/bin/python bench.py          # raw vs current + 게이트 (top-1 ≥85%, top-3 ≥95%)
venv/bin/python bench.py --all -v # 실험 변형 + 미스 쿼리
```

첫 실행이 `chrisryugj/kosimcse-roberta-multitask-onnx` 에서 모델(~106MB)을 `model/` 로
받는다. 맥미니 M-시리즈 기준 변형당 ~20초.

## 기준선 (2026-09-23, v3.8.9)

앱 임베더는 입력을 **128토큰**에서 자른다(`embedder/mod.rs` `MAX_LENGTH`, 배포 tokenizer.json 과
같은 값). 벤치 기본값도 128이다. 2026-09-22 기준선은 512토큰으로 재서 앱과 달랐다.

| 변형 | 청크 | top-1 | top-3 | MRR |
|---|---|---|---|---|
| raw (별표 유지, v3.8.7 이전) | 231 | 77% | 91% | 0.85 |
| **current** | 230 | **86%** | **100%** | 0.92 |
| +결재선 표 제거 | 219 | 93% | 100% | 0.97 |
| +제목 접두 | 230 | 93% | 100% | 0.97 |

절단 길이 비교(current): 128토큰 86%/100%/0.92, 256토큰 93%/95%/0.95, 512토큰 91%/98%/0.95.
질의 44개라 2~3건 차이는 오차 범위이고, 길이를 늘리면 임베딩 비용이 2.5~5배에 전체 재임베딩이
필요해 128을 유지한다(`--max-len` 으로 재현).

128토큰에서는 첫 청크의 결재선 표(문서번호·결재라인)가 토큰 예산을 먹어서, 표 제거나 제목 접두가
top-1 을 +7%p 올린다(512토큰에서는 차이가 없었다). 둘 다 임베딩 입력만 바꾸면 청크 오프셋·스니펫은
그대로 둘 수 있지만 전체 재임베딩과 장르 휴리스틱(결재문서 머리 줄 판정)이 걸려 다음 회차 후보로 둔다.

벤치는 벡터 단독이다. 실제 앱은 FTS5 키워드와 RRF 로 합치므로 절대값은 다르고, 여기서
보는 건 파이프라인 변경 전후의 **차이**다.

## 모델 비교 — EmbeddingGemma 2 (2026-10-27, 이슈 #47)

`--model eg2-int8|eg2-q4|eg2-fp32` 로 `onnx-community/embeddinggemma-2-ONNX` 를 같은 파이프라인에 넣는다
(질의 `task: search result | query: `, 문서 `title: none | text: ` 접두, 출력 `sentence_embedding`).
`speed.py` 는 앱 임베더 조건(CPU EP·최적화 Level3·서브배치 8)으로 청크당 시간과 최대 메모리를 잰다(맥 M 시리즈, 스레드 4).

| 모델 | 크기 | 128토큰 top-1 · top-3 · MRR | 512토큰 top-1 · top-3 · MRR | 128토큰 청크당 · 최대 메모리 |
|---|---:|---|---|---|
| KoSimCSE int8 (현행) | 106MB | 86% · **100%** · 0.92 | 91% · 98% · 0.95 | **19.6ms · 347MB** |
| EmbeddingGemma 2 int8 | 314MB | **91%** · 95% · **0.94** | 93% · 98% · 0.96 | 48.7ms · 1,120MB |
| EmbeddingGemma 2 q4 | 174MB | 86% · 95% · 0.91 | 95% · 98% · 0.97 | 121.9ms · 1,009MB |
| EmbeddingGemma 2 fp32 | 1,084MB | 91% · 95% · 0.94 | 93% · 98% · 0.96 | — |

128토큰에서 EmbeddingGemma 2 는 1위 적중이 2건 많지만 놓칠 때 깊게 놓친다(출장 여비 결재문서 질의가 27위·8위, KoSimCSE 는
미스 6건 모두 3위 안). 색인은 2.5배 느리고 메모리는 3배, 받는 모델은 3배이며 벡터가 호환되지 않아 전체 재색인이 든다.
질의 44개에서 2건 차이는 오차 범위라 기본 모델은 바꾸지 않는다. 긴 문맥(512토큰)으로 가면 품질이 오르지만 청크당 148ms 라
같은 512토큰 KoSimCSE(53ms)의 2.8배다.
